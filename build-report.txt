What changed in revision 11
----------------------------
A live run of revision 10's --release-frozen-only pulsed register 0x02 correctly (readbacks all
verified, 0xFD -> 0xFF -> 0xFD) and Frozen still never responded. Register 0x06 (direction/config)
was never touched by that revision. On the PCAL6416A, register 0x06 selects per-bit whether a pin
is an input/high-impedance (1) or an output (0); the power-on-reset default is every bit an input,
which ignores its output-latch value (register 0x02) entirely -- so revision 10's pulse changed
what the chip would drive if bit 1 were an output, not the physical pin. The original,
confirmed-working upstream reset sequence writes register 0x06 to 0xFC (bits 0 and 1 as outputs) as
one of its first two writes; this mode's narrow, bit-1-only analog of that write was missing.

  - `i2c::pulse_frozen_reset_bit` now does three writes instead of two: (1) prepares register
    0x02's output latch to the asserted level before bit 1 becomes an output, avoiding an
    unintended glitch; (2) configures only bit 1 of register 0x06 as an output, preserving bit 0
    and every other bit; (3) holds the now-actually-driven level for 100ms, then releases it.
    Every write's target is verified mathematically before being issued (generalized from a
    register-0x02-only helper to a shared one accepting either register) and every readback is
    verified after. Register 0x06 is deliberately never restored -- the reset line must stay
    actively driven -- and register 0x07 is still never written.
  - `report::ReleaseFrozenOnlyResults` gained `original_register_0x06`/`config_register_0x06`/
    `config_readback_register_0x06`/`config_readback_matches`/
    `bit1_was_already_configured_as_output`.
  - 4 net new tests (166 total in this directory, up from 162), all in `i2c.rs`: the two starting
    cases explicitly requested (config register 0x06 = 0xFF -> 0xFD, and 0xFC -> unchanged), an
    exhaustive 256-value sweep proving the configuration write can only ever change bit 1, an
    ordering test proving the output-latch write happens strictly before the direction write, and
    a renamed/updated test proving register 0x07 is never written across the same sweep. See
    TEST_RESULTS.md for the full writeup.

What changed in revision 10
----------------------------
A live run of `--release-frozen-only` (revision 9) found register 0x02 already reading `0xFD` (bit
1 already low) at the point of release, so that revision's one-shot `released = original & !0x02`
was a no-op -- no write ever changed the register, no edge appeared on the pin, and Frozen never
responded. Release is a transition, not a level: the previously-confirmed working reset sequence's
last two writes are `0x02 <- 0xFF` (assert) then `0x02 <- 0xFD` (release), a low->high->low pulse.

  - New `i2c::pulse_frozen_reset_bit` replaces `i2c::release_frozen_reset_bit_only` (removed):
    always asserts bit 1 first (`asserted = original | 0x02`), holds it 100ms
    (`i2c::PULSE_SETTLE`), then releases it (`released = asserted & !0x02`) -- both values computed
    from what was actually read at each step, never hardcoded -- verifying the readback and
    re-checking only-bit-1-changed after each of the two writes independently. The shared
    `read_modify_write_reg02` helper now also asserts (not merely logs) that the computed target
    cannot change any bit other than bit 1 before either write is issued. Neither write ever
    touches registers 0x06/0x07.
  - The post-release Ping sequence was hardened on the same evidence: after the pulse, this mode
    now waits up to 2 seconds for boot messages, then Pings repeatedly for up to 10 more seconds,
    tolerating any interleaved startup messages instead of failing on the first non-Pong packet,
    before concluding Frozen never responded and aborting without ever sending Prime. This is not
    treated as a fault -- no automatic reset is asserted for a non-responsive Frozen, only for a
    genuine firmware-reported pump fault (unchanged from revision 9).
  - The `RESERVOIR INDICATOR IS STILL WORKING` confirmation is now asked only once Frozen has
    actually reached application firmware, immediately before Prime. Its outcome is reported via a
    new three-state `ReservoirStatus` (Confirmed / FailedByOperatorObservation / Unverified)
    replacing the previous plain boolean, so a run that aborted before ever asking is never
    conflated with one where the operator was asked and said no. The previous automatic
    capwater-unavailable check that gated Prime in revision 9 was removed; capwater/flowrate
    mentions observed during the boot-message wait are still logged and reported, but only the
    operator's own confirmation gates Prime now.
  - `report::ReleaseFrozenOnlyResults` gained `asserted_register_0x02`/`asserted_readback_register_0x02`/
    `asserted_readback_matches`/`released_readback_register_0x02`/`released_readback_matches`/
    `pulse_duration_ms`/`reservoir_status` and lost `changed_bit_mask`/`readback_register_0x02`/
    `readback_matches`/`reservoir_sensor_operational_after_release`.
  - 4 net new tests (162 total in this directory, up from 158): 3 net new in `i2c.rs` (5
    `release_frozen_reset_bit_only_*` tests removed, 7 pulse tests added -- including both starting
    cases requested (0xFD and 0xFF), an exhaustive 256-value sweep proving only bit 1 ever changes
    across both halves of the pulse, and the same sweep proving 0x06/0x07 are never written), and 1
    net new in `prime_opensleep_init.rs` (the now-obsolete capwater-gates-Prime test removed;
    `pulses_correctly_even_when_register_already_reads_0xfd` and
    `aborts_without_prime_when_frozen_never_answers_ping` added). See TEST_RESULTS.md for the full
    writeup.

What changed in revision 9
---------------------------
Added `--release-frozen-only` to `frozen-prime-opensleep-init`, replacing both the global upstream
reset (`opensleep::reset::ResetController`, revision 7/8's approach) and the earlier
`--preserve-boot-state` flag (removed in revision 7) with a third, narrower startup mode. Real
hardware evidence drove this: after a normal boot the reservoir-fill indicator works but Frozen
doesn't answer `Ping`; running the full reset sequence does release Frozen, but also turns the
reservoir indicator off and leaves it unresponsive -- firmware then reports `[fdc1004] failed to
write config` and `[capwater] sensor unavailable`. Tracing which single write in the four-register
reset sequence actually releases Frozen showed it is the last one, which changes I2C expander
(`0x20`) register `0x02` from `0xFF` to `0xFD` -- clearing bit 1 and nothing else; registers `0x06`
and `0x07` (port direction/config) are never involved in releasing Frozen, and are suspected to be
what disturbs the reservoir indicator.

  - New `i2c::release_frozen_reset_bit_only`/`assert_frozen_reset_bit_only`: narrow,
    read-modify-write single-bit operations (`released = original & !0x02` /
    `asserted = current | 0x02`) that read register `0x02` back and report whether the readback
    matched and whether any bit other than bit 1 changed -- the run aborts before ever opening the
    Frozen UART if either check fails. Neither function writes registers `0x06`/`0x07` under any
    circumstances (proved by 5 new `i2c.rs` unit tests, including one sweeping every possible
    original register value and one using a stale-readback mock transport to prove the mismatch
    path is actually reachable).
  - This mode drives Frozen through this binary's own audited `FrozenLink`/`AuditedTransport`
    (`Mode::PrimeTest` -- the same runtime mode `frozen-prime-test` uses), not the real upstream
    scheduler plain `frozen-prime-opensleep-init` uses -- so `Prime` remains reachable through
    `AuditedTransport` in exactly one runtime mode, now reached from two call sites instead of one.
    `main.rs`'s `frozen_action_prime_is_referenced_only_in_safety_and_prime_test` guardrail was
    updated to permit `prime_opensleep_init.rs` as the second permitted file.
  - A third, required typed confirmation phrase (`RESERVOIR INDICATOR IS STILL WORKING`) is asked
    immediately before `Prime` -- after Frozen has reached firmware and startup messages have been
    observed, not at the start of the run like the other two phrases.
  - `Prime` is only sent if `[capwater] sensor unavailable` was not observed after release; the new
    `reservoir_sensor_operational_after_release` report field records the inverse of that
    observation directly, since capwater is exactly the sensor behind the reservoir indicator.
  - On normal completion (`"done"` or `"done because empty"`), this mode performs no I2C write at
    all on exit -- unlike plain `frozen-prime-opensleep-init`, which still performs an emergency
    reset write on a pump fault using the shared, hardcoded-0xFF `assert_reset`, this mode's own
    emergency path (`assert_release_only_emergency_reset`) uses the same narrow, bit-1-only
    read-modify-write as the release itself.
  - `--dry-run --release-frozen-only` runs end to end against a mocked I2C expander and a new
    proactive mock Frozen device (`mock::spawn_mock_frozen_device_release_only`) that pushes
    priming-completion messages on its own short timer rather than piggybacked on
    `GetTemperatures` polls (the existing shared mock's design, built for `frozen-prime-test`'s
    tick-based active loop) -- because this mode never polls `GetTemperatures` at all, matching
    real Frozen firmware's own unsolicited push behavior over UART.
  - 13 new tests (158 total in this directory, up from 145): 5 in `i2c.rs`, 8 in
    `prime_opensleep_init.rs::tests::release_frozen_only` (dry-run end-to-end via the public `run()`
    entry point, the reservoir-phrase requirement, the bootloader-to-firmware jump path, the
    capwater-unavailable refusal, the done-vs-done-because-empty distinction, the I2C-read-failure
    abort path, and a full-run assertion that only register `0x02` is ever written and only its bit
    1 ever changes). Smoke-tested against the actual cross-compiled binary via qemu-aarch64-static:
    `--help` output, a full dry-run to `"[priming] done"` with JSON output verified field-by-field,
    and the reservoir-phrase-mismatch refusal path (exit code 30).

The first attempt at this revision's build failed its own QEMU test run: two new tests
(`obsolete_devkit_uart_paths_are_never_hardcoded_anywhere` and
`frozen_run_is_never_called_with_the_upstream_port_constant`) had a self-matching bug -- each
scanned this file's own source for a needle written as a contiguous literal, which matched the
assertion's own source text (the same class of bug this codebase's other guardrail tests already
avoid by building needles from split fragments). Fixed and reverified (both fixed tests plus the
full `prime_opensleep_init::`/`guardrail_tests::` modules, 17 tests, run locally) before the
successful rebuild below.

What changed in revision 8
---------------------------
A live run on this Hub completed the real subsystem reset and then failed immediately with
`Serial Io(NotFound): No such file or directory`: `frozen-prime-opensleep-init` (added in revision
7) was calling the real `opensleep::frozen::run` with the upstream `opensleep::frozen::PORT`
constant (`/dev/ttymxc2`, correct for the MT8365 devkit the pinned upstream source targets), which
this Hub does not expose. This Hub uses `/dev/ttyS1` for Frozen (still the unmodified upstream
38400 baud) and would use `/dev/ttyS2` for Sensor if Sensor were ever retained here.

  - `frozen::run`'s `port` argument is now a locally-defined `FROZEN_UART_PATH` constant
    (`/dev/ttyS1`), passed explicitly. `opensleep::frozen::PORT` now appears in
    `prime_opensleep_init.rs` only as the comparison value in a logged override message
    (`"Frozen manager UART override: /dev/ttymxc2 -> /dev/ttyS1"`), logged before opening, and is
    never passed to anything that opens a port. Nothing about `frozen::run`'s protocol, wake
    sequence, or state machine changed -- only the device path handed to it.
  - A new preflight check refuses to proceed -- before touching I2C at all -- if `/dev/ttyS1` does
    not exist.
  - The Sensor subsystem, previously run best-effort in the background (revision 7), is now removed
    from this mode entirely: it is a separate physical UART with no bearing on Frozen priming or on
    `capwater`/`flowrate` reporting, so the surest way to guarantee it "must not prevent priming" is
    to never run it, not to run it best-effort and have to keep proving its failures stay
    non-blocking. `main.rs`'s `sensor_subsystem_is_never_referenced` guardrail test (carved out for
    this file in revision 7) is back to its original, stricter form: no file may reference
    `opensleep::sensor`/`sensor::run`, `frozen-prime-opensleep-init` included.
  - `OpenSleepInitResults` gained `frozen_uart_requested`, `frozen_uart_opened`, and
    `frozen_manager_task_running` fields (and lost the now-meaningless `sensor_subsystem_started`/
    `sensor_subsystem_error`). `frozen_uart_opened` distinguishes "the port opened" from "a task
    was merely spawned" by racing the manager's future against a 500ms window immediately after
    starting: an open failure resolves near-instantly, while a successful open keeps the future
    pending for at least ~100ms on its own (`FrozenState::publish_reset`'s MQTT publish, wrapped in
    a 100ms timeout this mode's never-polled event loop cannot complete) before reaching its main
    loop.
  - 3 new tests (145 total in this directory, up from 142): a constant-value regression test and a
    source-scan test local to `prime_opensleep_init.rs`, plus a new `main.rs` guardrail test
    scanning this binary's entire source for `/dev/ttymxc0`/`/dev/ttymxc2`/`/dev/ttymxc` as
    hardcoded literals. See TEST_RESULTS.md for the full writeup, including what has and has not
    been verified for this revision.

What changed in revision 7
---------------------------
Removed `--preserve-boot-state` (added in revision 6) and replaced it with a new subcommand,
`frozen-prime-opensleep-init`. Real hardware evidence showed `--preserve-boot-state`'s approach --
skip I2C entirely to avoid resetting the subsystem -- was the wrong fix: it left Frozen in a state
where the reservoir-level (`capwater`) sensor was not reliably operational. Skipping I2C access
was never actually the goal; a full, *correct* initialization was.

`frozen-prime-opensleep-init` performs the same Prime-once operation through the real, unmodified
upstream OpenSleep initialization and Frozen manager code --
`opensleep::reset::ResetController::reset_subsystems`, the real LED controller, a real (never
network-connected) `MqttManager`, a best-effort real Sensor subsystem task, and -- doing all of the
actual work -- the real `opensleep::frozen::run` manager -- instead of either this binary's own
reimplemented reset/transport (`frozen-prime-test`) or a custom partial reset
(`--preserve-boot-state`). See `src/bin/opensleep-diagnostic/prime_opensleep_init.rs`'s module
docs and SAFETY.md for the full design rationale.

  - `Prime` is triggered without any command channel (none exists in the pinned upstream source):
    this mode constructs an in-memory configuration with `prime` set to "now", which the real
    Frozen scheduler's own internal debounce/matching-window logic (unmodified) then fires at most
    once on its own, the same as it would for a real end user's scheduled priming time.
    `away_mode` is deliberately left `false` (setting it `true` would also block the Prime
    schedule, not just the temperature schedule); temperature targets are kept disabled instead via
    an empty temperature profile, which the real scheduler already treats as "always disabled".
  - Since the real, unmodified code has no observer hook of its own, a new `log_tap` module taps
    the one global logger this binary already installs to observe the exact log lines that code
    emits (`"Message: FW: [capwater] sensor unavailable"`, `"Priming Message: done"` /
    `"...done because empty"`, etc.) without modifying that code at all.
  - If firmware reports `[capwater] sensor unavailable` as a result of this run's own
    initialization, `Prime` is never sent, and the initialization sequence/subsystem state that
    produced it is printed.
  - The observation window is fixed at the firmware-reported priming duration (600000 ms).
  - On normal completion or "done because empty", this mode does *not* assert the I2C subsystem
    reset -- Frozen's own firmware returns to idle on its own, and forcing a reset right after using
    the real initialization path would be needlessly disruptive to a subsystem this mode is
    specifically trying to leave in its normal, running state. The one exception is a genuine
    firmware-reported pump fault, which does assert an emergency reset via this diagnostic's own
    already-audited `assert_reset` primitive (not upstream's reset sequence).
  - Shutdown reuses the exact mechanism real `main.rs`'s own top-level `tokio::select!` already
    uses: the real `frozen::run`/`sensor::run` futures turned out not to be `Send` (both hold a
    `tokio::sync::watch::Ref` internally), so they are polled directly via `tokio::select!` in the
    same task rather than `tokio::spawn`-ed, and are simply dropped (cancelled) when the function
    returns -- there is no `.abort()` anywhere in this file.
  - `main.rs`'s `guardrail_tests` were rewritten: four tests that previously asserted Sensor/MQTT/
    the LED driver/the real Frozen manager are never referenced anywhere now assert they are
    referenced *only* by `prime_opensleep_init.rs` -- and that even that file never references the
    real config-file loader or `rumqttc` directly.
  - 8 net new tests (5 removed with `--preserve-boot-state`, 13 added): 8 in
    `prime_opensleep_init.rs`, 4 in the new `log_tap.rs`, and 1 in the new `confirm.rs` (the
    interactive-phrase helper extracted out of `prime_test.rs` so both Prime-sending modes share
    one implementation). Because the real upstream code hardcodes real serial ports/I2C devices
    with no mock transport to substitute, this mode's happy-path behavior cannot be exercised by an
    automated mock-based test the way this binary's other subcommands are -- see TEST_RESULTS.md
    for what was and wasn't verified this way.
  - Smoke-testing the actual cross-compiled binary (not just `cargo test`, which cannot catch
    CLI-surface or output-formatting bugs) found and fixed three issues before this release: clap's
    automatic kebab-case naming split "OpenSleep" into "open-sleep" (`frozen-prime-open-sleep-init`
    instead of `frozen-prime-opensleep-init`, fixed with an explicit `#[command(name = ...)]`); two
    of `log_tap`'s own tests raced on its process-global state when `cargo test` ran them in
    parallel (fixed with a `Mutex` serializing that module's own tests against each other; verified
    with 15 consecutive `--test-threads=8` runs); and `--dry-run` reported `exit_code: 30` in its
    own summary/JSON despite the process actually exiting 0, and never wrote `--json-output` at
    all, unlike every other subcommand's `--dry-run` (fixed, with new tests for both).

What changed in revision 5
---------------------------
Added a fourth subcommand, `frozen-prime-test`, which intentionally sends `Prime` (opcode 0x52)
exactly once to fill an empty or partially-filled hydraulic loop. Full source audit (does Prime
take arguments, apply to one/both sides, have an acknowledgment/start/completion signal, have a
cancellation command, or have an assumed duration; what pumps/valves/solenoids are expected to
operate) is in PROTOCOL_AUDIT.md. Key findings that shaped the implementation:

  - `Prime` takes no arguments and has no per-side field -- it always affects both sides in one
    frame (`7E 01 52 B6 2B`, asserted byte-for-byte by upstream's own test_prime fixture). This is
    why frozen-prime-test has no --side flag, unlike frozen-cool-test.
  - Direct start evidence: the binary `PrimingStarted` packet (0xD2) and/or a decoded
    "FW: [priming] start" message. The *only* completion evidence that exists anywhere in the
    protocol is "FW: [priming] done" / "...done because empty" -- there is no binary
    "priming complete" packet, so this mode's early-stop-on-completion logic is driven entirely by
    that message text.
  - No Prime-cancellation command exists anywhere in the reused protocol (confirmed by a full scan
    of FrozenCommand's variants). Subsystem reset (I2C 0x20) is therefore the only forced-stop
    mechanism, exactly as for every other mode -- frozen-prime-test runs the same shared safe-stop
    routine on every exit path, including after "done" was already observed.
  - Normal OpenSleep's own scheduler does not assume any priming duration: its `prime` config
    field is a time-of-day, not a duration, and its own source contains a
    "// TODO verify it actually started priming" comment acknowledging no reliable completion
    tracking exists upstream either. frozen-prime-test's 5-60s bounds (default 30s) are therefore a
    deliberately conservative compile-time choice, stated as such rather than presented as
    spec-derived.
  - No "solenoid" or "valve" message exists anywhere in the pinned source; that detection is
    documented as a forward-compatible keyword scan, not a confirmed protocol feature.
  - `Prime` is gated by two independent mechanisms: the existing per-mode whitelist (extended with
    a new `Mode::PrimeTest`), and a new at-most-once check inside `AuditedTransport::check` itself
    -- a second `Prime` attempt in the same run is refused at the transport layer, not merely
    avoided by this binary's own control flow. A new source-level guardrail test
    (`frozen_action_prime_is_referenced_only_in_safety_and_prime_test`) proves
    `FrozenAction::Prime`/`FrozenAction::prime()` is never referenced outside `safety.rs`/
    `prime_test.rs`.
  - `frozen-prime-test`'s result reporting never marks the run PASS merely because the command was
    sent, acknowledged, a pump showed voltage, or "done" was printed -- it requires either a direct
    firmware reservoir-transition message or the operator confirming both water movement and a
    dropped reservoir level; otherwise the result is INCONCLUSIVE.
  - Two bugs were found and fixed during this revision's own smoke-testing (not present in the
    delivered build): an over-throttled telemetry-polling cadence that was incompatible with the
    2-second staleness threshold, and a pre-existing bug (also affecting frozen-cool-test, fixed
    here too) where several JSON report fields were being set on the in-memory Report *after* it
    had already been written to disk, so the file never reflected them. Both are covered by new
    automated tests and re-verified against the real cross-compiled binary via qemu-aarch64-static.

What changed in revision 4
---------------------------
Corrected `frozen-cool-test`'s active-test preflight and safety monitoring based on evidence from
a real `frozen-passive` run and closer reading of the exact upstream source. Full account in
PROTOCOL_AUDIT.md and TEST_RESULTS.md; summary:

  - `TemperatureUpdate.error` is a control-loop error term in degrees C, not a fault/status code
    (source doc comment: "error in deg celcius"; real captured telemetry consistently reports 9
    with no other sign of a fault). Renamed to `control_error_c` in JSON/CSV output and confirmed
    to never gate any pass/fail/abort decision -- `cool_test::evaluate_tick` doesn't even take
    this field as a parameter.
  - Baseline collection and active-phase safety monitoring now rely exclusively on the unsolicited
    `TemperatureUpdate` push (opcode 0x41), not the solicited `GetTemperature` reply (opcode
    0xC1): real hardware has been observed sending a 14-byte 0xC1 frame, while the reused,
    unmodified parser requires exactly 27 bytes and so never decodes it. The solicited reply is
    still requested each tick (via a new `FrozenLink::send_only` fire-and-forget primitive) and
    preserved/logged as raw evidence when it does decode, but nothing safety-relevant depends on
    it anymore.
  - `[capwater]`/`[flowrate]` sensor-unavailable firmware messages are recorded as warnings, not
    treated as fatal (observed persisting with the cover connected and the reservoir filled; flow
    itself is not exercised until a pump actually runs).
  - New evidence-gated active-phase abort conditions: the selected pump still reporting off/0V
    more than 3 seconds after being enabled; a firmware message reporting the selected TEC locked;
    Frozen disabling the selected side on its own; a firmware fault-keyword message
    (overtemperature/overcurrent/shutdown/fault/failed/locked) after a 2-second startup grace
    period, with a documented carve-out for the evidenced, benign "flash locked" message; and the
    operator typing a report of a leak/smell/noise (or the literal word ABORT) during the active
    phase, read from a background stdin watcher started only after every confirmation-phrase read
    is complete.
  - `frozen-cool-test`'s default duration changed from 15 to 10 seconds for a first test; the hard
    30-second maximum, the 2.0C max delta, and the 15-35C baseline range are all unchanged.
  - Pump operation can now be reported PASS (not just UNVERIFIED) from decoded firmware voltage
    evidence, and FAIL if the most recent such message reports 0V/off -- still never PASS merely
    because the enable command was accepted.

What changed in revision 3
---------------------------
Complete redesign from a single-pass, read-mostly Frozen+Sensor probe into a staged,
Frozen-only diagnostic with three explicit subcommands:

  opensleep-diagnostic frozen-passive
  opensleep-diagnostic frozen-cool-test
  opensleep-diagnostic emergency-stop

The Sensor subsystem and the LED controller's write path are no longer referenced anywhere in
this binary's source (verified at test time by main.rs's guardrail_tests, which scan this
binary's own source files for forbidden references). `frozen-passive` never enables an actuator
command and is safe with the cover disconnected and no water. `frozen-cool-test` intentionally
activates exactly one cooling channel, gated behind four required --confirm-* flags and two
exact typed confirmation phrases, hard-coded limits (max 2.0C delta, max 30s duration, 15-35C
baseline range) that no CLI flag can override, and a shared safe-stop routine (three repeated
disable-both-sides sends, UART flush, I2C reset assert) that runs on every exit path including
Ctrl+C/SIGTERM/SIGHUP, timeout, communication/telemetry errors, and (via a catch_unwind boundary
around the per-tick evaluation logic) an internal panic. `emergency-stop` is an independent,
config/MQTT/Sensor/LED-free fast path that best-effort-disables both sides and unconditionally
asserts the I2C reset, returning non-zero if that reset could not be confirmed.

`Prime` and `Random` are structurally unreachable: the closed FrozenAction enum
(src/bin/opensleep-diagnostic/safety.rs) has no variant for either, so this binary's own command
type cannot represent them, independent of any runtime whitelist. See SAFETY.md and
PROTOCOL_AUDIT.md for the full command/evidence audit.

A --dry-run flag on every subcommand performs no I2C or UART writes and instead runs the same
code paths against a mocked Frozen device and a mocked I2C bus, so the full flow (including the
interactive confirmations) is testable on an ordinary development machine.
