What changed in revision 22
----------------------------
Every prior active mode is a bounded, host-observed session. This revision adds a genuinely
different shape: a one-shot configuration transaction that sets a fixed target and exits, leaving
Frozen firmware to run it indefinitely -- exactly how stock OpenSleep's own scheduled
SetTargetTemperature calls already work, just triggered manually instead of by a schedule.

  - Added frozen-hold-start --target-c <C> (or --left-target-c/--right-target-c together, both
    required): sends one absolute SetTargetTemperature(enabled=true) per side -- no baseline, no
    delta, validated against the same 0-45C backstop frozen-cool-test's own --target-c already
    used (extracted into a shared validate_absolute_target_centideg helper so there is still only
    one operating-range constant) -- requires an exact matching TargetUpdate confirmation for
    each, prints the required confirmation banner, and exits.
  - After both confirmations, sends zero further Frozen commands of any kind: no disable, no
    independent shutdown guard, no Drop-based shutdown, no duration timer, no firmware-message
    interpretation, no pump/TEC/fan observer, no host thermal watchdog, no reaction to priming or
    tec[...] locked (pump) messages -- there is no code path left to run once the confirming
    function returns, regardless of process exit, descriptor close, or a UART disconnect
    afterward.
  - Never resets a Frozen that is already responsive (it may be adjusting targets on a Frozen a
    previous frozen-hold-start already brought up). Startup is "probe first, reset only if
    silent": a bounded, reset-free Ping probe runs first; only if Frozen never answers does this
    fall back to the already-audited, unmodified frozen_startup::start_frozen_narrow. Register
    0x07 is never written on either path.
  - Partial-transaction rollback (disable the confirmed side if the other never confirms) before
    success is declared; once both sides confirm, that path is structurally unreachable.
  - Added frozen-hold-stop: Pings first (logging only, never to justify a reset), then disables
    both sides via a new, independent repeated-disable-and-confirm loop (deliberately not calling
    into cool_test.rs's own shutdown directly, since this one must never parse firmware message
    text and must never fall back to asserting the I2C reset), requiring confirmation of both
    sides before exiting successfully.
  - Added frozen-hold-status: strictly non-controlling, Ping/GetTemperatures only -- never
    SetTargetTemperature in either direction, never resets Frozen, never touches PCAL state. Safe
    to run at any time, including while frozen-hold-start's targets remain active.
  - New closed action FrozenAction::HoldTarget serializes to the identical SetTargetTemperature
    wire frame EnableCooling already produces (no new opcode); reachable only in the new
    Mode::HoldStart, refused everywhere else (including frozen-cool-test) by the same exhaustive
    per-mode match every other action already goes through.

14 net new tests, all in frozen_hold.rs (361 total, up from 347). Every other existing test file
was re-run unmodified against this revision and still passes -- enable_cooling's own behavior is
unchanged; only its internal range check was extracted into the shared helper hold_target now also
calls. See TEST_RESULTS.md for the full writeup.

What changed in revision 21
----------------------------
Revision 20's bit-0-only experiment left Sensor completely silent at both known baud rates, and
register 0x06 read 0xFE afterward -- bit 1 (Frozen's own, already-proven reset line) was still an
input. A separate critical observation: this Hub's actual register 0x07 reads 0x77, not upstream's
0x31 -- a strong candidate for why the old global reset broke capwater/reservoir-related hardware.

  - Added --combined-narrow-subsystem-init (opt-in; cannot be combined with
    --enable-suspected-sensor-line, --restore-suspected-sensor-line, or --audit-expander):
    reproduces only the port-0 portion of upstream's own startup -- bits 0 and 1 of registers
    0x02/0x06 -- in three writes (assert both bits HIGH on 0x02, configure both as outputs on
    0x06, hold ~100ms, release only bit 1 back LOW on 0x02, reproducing Frozen's own already-proven
    pulse exactly), a dedicated independent helper rather than a composition of the existing
    single-bit functions. Verified before proceeding; aborts before any UART probing on a
    mismatch. Never touches register 0x07 or 0x03 -- proven, not assumed, via a full expander
    audit captured both before and after.
  - After a verified sequence, verifies Frozen is reachable with a single Ping (Mode::Passive's
    whitelist -- no temperature target, no Prime, no pump, no cooling; reuses
    frozen_ops::ping/jump_to_firmware_and_wait unmodified, never constructing a raw
    FrozenAction/FrozenCommand directly), then probes Sensor using upstream's own bootloader-first
    discovery ordering, tracking best-effort /proc/tty/driver/serial byte counters and
    elapsed-time-to-first-byte/packet as additional evidence.
  - This is the one deliberate, narrow exception to sensor-probe never touching Frozen --
    main.rs's sensor_probe_never_touches_frozen guardrail test now describes exactly that
    exception instead of a blanket ban.
  - State is left as configured on exit; there is no --restore option for this mode in this
    version.
  - Fixed a small reporting-fidelity gap caught during this work: when the I2C device fails to
    even open, the combined-init register fields now correctly report None (never read) instead
    of a misleading Some(0x00).

What changed in revision 20
----------------------------
Real hardware evidence narrowed the candidate Sensor enable/reset-release/power-enable line to one
specific bit: /proc/tty/driver/serial confirms ttyS2 is the only remaining real MMIO UART besides
Frozen's ttyS1, plain sensor-probe against it shows transmitted bytes but zero RX at both known
baud rates, and upstream OpenSleep's own reset sequence configures register 0x06 to 0xFC (bits 0
and 1 both outputs) and keeps register 0x02 bit 0 HIGH throughout -- never pulsing it low -- while
this fork's own proven narrow Frozen-only initialization leaves register 0x06 at 0xFD (bit 0 still
an input). Only bit 0 differs between the two initialization paths, and upstream never drives it
low.

  - Added --enable-suspected-sensor-line: opt-in, never implied by --passive/--ping/--discover/
    --query-info. A dedicated, independent helper (i2c::configure_suspected_sensor_enable_high --
    deliberately not a reuse of pulse_frozen_reset_bit, bit 1's own helper) configures only bit 0
    of registers 0x02/0x06 as an output, driven HIGH -- never a pulse, never LOW, never bit 1,
    never register 0x07, never a whole-register constant. Every write's changed-bit mask is
    verified to be a subset of {0x00, 0x01} before proceeding; a mismatch aborts before any Sensor
    UART probing at all (overall_result: expander_verification_failed). Waits 500ms, then mirrors
    upstream's own bootloader-first discovery ordering when combined with --discover (the reverse
    of plain --discover's firmware-first order), or, combined with --passive, sends zero further
    Sensor UART writes and just listens, recording the elapsed time from the enable sequence
    completing to the first raw byte/decoded packet.
  - Added --restore-suspected-sensor-line (requires --enable-suspected-sensor-line in the same
    invocation): restores only bit 0 of 0x02/0x06 to the value this same invocation captured
    before enabling, preserving every other bit as it exists at restore time. Never automatic on
    normal exit -- if bit 0 really is a Sensor enable line, reverting it would immediately disable
    the Sensor MCU again and make the experiment impossible to interpret.
  - Added ~20 new report fields (reg_0x02_*/reg_0x06_* four-tuples, port0_bit0_* booleans,
    passive_rx_before/after_enable, first_rx/first_decoded_packet_after_enable_ms,
    frozen_uart_opens) and five new overall_result states (sensor_alive_after_line_enable,
    sensor_bootloader_after_line_enable, spontaneous_sensor_traffic_after_line_enable,
    still_silent_after_line_enable, expander_verification_failed).
  - Caught and fixed two bugs before release: a latent guardrail-test gap from revision 19 itself
    (cli.rs's own doc comment contained the literal substring the guardrail test bans, undetected
    until this revision's full test re-run), and a test that incurred a real 60-second wait from
    an unset --observe-seconds override (fixed to well under 1s).

23 net new tests (332 total, up from 309). See TEST_RESULTS.md for the full writeup.

What changed in revision 19
----------------------------
Added a sixth subcommand, sensor-probe, establishing reliable UART communication with the Sensor
MCU (presence/piezo/temperature board -- a separate physical UART from Frozen, /dev/ttyS2 by
default on this Hub) and decoding whatever is already available. Deliberately does not attempt
presence calibration, piezo configuration, vibration actuation, alarms, or expander reset pulsing
in this version.

  - --passive (default): zero UART writes, zero I2C writes. Opens /dev/ttyS2 at each known Sensor
    baud (115200 firmware, 38400 bootloader) in turn, listens for --listen-seconds (default 20),
    and decodes through the real, unmodified PacketCodec<SensorPacket> -- never aborting merely
    because a frame doesn't decode.
  - --ping: may send Ping (firmware baud first, up to 3 tries; only if silent, bootloader baud, up
    to 3 more), and nothing else -- never JumpToFirmware. Still zero I2C writes.
  - --discover: implements upstream's own Ping / JumpToFirmware discovery sequence (firmware Ping
    first; only if silent, bootloader Ping; only if bootloader responded, exactly one
    JumpToFirmware followed by a re-ping at firmware baud), but never starts the normal Sensor
    CommandScheduler and never sends any actuator/config command -- SensorProbeAction is a closed
    four-variant enum with no such variant to construct. --query-info (only after a confirmed
    firmware-mode Ping) additionally permits exactly two read-only queries already present in
    upstream SensorCommand: GetHardwareInfo/GetFirmwareHash. Once communication is established,
    listens for unsolicited traffic for --observe-seconds (default 60), tallying every packet type
    seen and computing per-side capacitance/piezo min/max/latest values.
  - --audit-expander (combinable with any mode): read-only PCAL6416A register dump (0x00-0x07, hex
    and binary) -- this feature's own files contain no write_reg call at all, so every register,
    including 0x02/0x06/0x07 (the ones the Frozen investigation proved sensitive), is structurally
    unwritable here.
  - Port-0 bit 0's function is deliberately left unproven: no reset/enable line pulsing of any kind
    is implemented in this version. If Sensor stays silent after UART discovery, this stops and
    reports the evidence (overall_result: "uart_silent", explicitly documented as not a hardware
    failure) rather than guessing.
  - Caught and fixed a bug before release: an early try_ping implementation could mistake an
    unsolicited telemetry packet (interleaved with a solicited response, as real Sensor firmware
    can do) for the awaited Pong, or exhaust its retry budget consuming unrelated packets while the
    real response sat unread. Fixed with a drain-until-match helper (send_and_wait_for) instead of
    treating any non-matching packet as a failed attempt.

35 net new tests (309 total, up from 274). See TEST_RESULTS.md for the full writeup.

What changed in revision 18
----------------------------
A 900-second right-side --firmware-authoritative cooling test completed successfully (target
reached and maintained, pump/fan/TEC evidence PASS, 0 of 1200 firmware-reported temperature reads
failed, both targets confirmed disabled, verified shutdown, no emergency reset) -- conclusively
demonstrating the former 900-second/15-minute duration ceiling was an artificial host-side test
limitation, not a demonstrated Frozen firmware limitation.

  - Removed the hard-coded 900s maximum duration entirely, across the CLI, safety checks,
    reporting, and docs. Every active test still requires an explicit, finite duration (no "run
    forever" mode), but there is no diagnostic-imposed maximum: a value is only rejected for being
    zero, failing to parse, being unrepresentable as a std::time::Duration, or causing the
    monotonic deadline computation to overflow (checked arithmetic throughout). New --duration
    <DURATION> accepts human-readable values (30m, 1h, 4h, 8h30m) via the integer-backed humantime
    crate (never floating-point hours), mutually exclusive with the pre-existing --duration-seconds
    (kept for backward compatibility); neither given still defaults to 120s. --confirm-extended-test
    was removed along with the ceiling it gated -- the four existing --confirm-* flags are
    sufficient acknowledgement; a duration above 300s now only prints a reminder.
  - Extended --side with a "both" value for simultaneous left+right operation in the same bounded
    test, always requiring --firmware-authoritative (the legacy loop's per-tick host-side heuristics
    are single-side only by design). Side::Both is never itself represented on the wire: Frozen
    still receives one ordinary SetTargetTemperature for Left and one for Right, sent back-to-back
    with no unrelated polling interleaved. --target-c with --side both sends the same absolute
    target to both sides (each independently validated against its own baseline); --delta-c with
    --side both applies the same delta independently to each side's own baseline (targets may
    differ slightly). Active observation never begins until both sides' enabled TargetUpdate is
    explicitly confirmed; a partial enable (only one side confirms) is its own terminal condition
    (partial_dual_side_enable) that immediately disables both and never continues with one side
    active. A fault on either side stops both sides together.
  - Hardened the independent shutdown guard (the separate OS process backstopping the main process
    crashing, hanging, or being killed) for runs that can now legitimately last hours. It previously
    only detected the main process exiting (its stdin pipe closing); it now also requires a periodic
    heartbeat byte from within the main process's own per-tick active loop (10s interval, 45s
    timeout) -- a genuinely stuck loop, not just a dead process, now triggers the same immediate
    controlled disable. The guard also runs in its own process group (immune to a SIGHUP delivered
    to the parent's controlling terminal) and separately consumes SIGINT/SIGTERM/SIGHUP itself in a
    loop that never exits on any of them.
  - Fixed a target_reached: true / time_to_target_seconds: None reporting bug in
    --firmware-authoritative mode: the boolean was set but the elapsed time was never actually
    recorded. Now measured from each side's own enable confirmation to its own target being reached,
    tracked independently per side so one side reaching target first can never overwrite the other's
    value.
  - Added the dual-side report fields (per-side baseline/target/confirmed/reached/time-to-target/
    pump/TEC-current/shutdown-observed fields, independent_guard_activated, requested_side_mode),
    populated for --side both runs and populated from the requested side alone for a one-side run.
    "Emergency shutdown: PASS" in the printed report is now "Controlled shutdown: PASS" for
    frozen-cool-test, unless the narrow emergency I2C reset genuinely fired.
  - Added per-minute progress logging for both the one-side and --side both active phases, instead
    of repeating every unchanged reading at INFO level.

What changed in revision 16
----------------------------
A live cooling test enabled the selected side successfully -- pump commanded, solenoid opened,
water audibly flowing -- but stopped seconds later with pump_startup_failure. Root cause: three
"pump[left] off @ 0.000000V" reports were already sitting in the host's read buffer from before the
enable command was even acknowledged; the active loop had no way to tell that stale, pre-enable
evidence apart from a genuine post-enable failure. A host-side telemetry race, not evidence the pump
had actually failed.

Rather than patch the legacy active loop's heuristics again, this revision adds a completely
separate, opt-in active-phase mode -- --firmware-authoritative -- alongside the legacy loop, which
is otherwise entirely unchanged (every pre-existing test, unmodified, still passes).

  - Enable confirmation now waits for the specific enabled TargetUpdate, not merely "some reply
    arrived" (the legacy loop's send_result.is_ok() shortcut -- exactly the gap that let buffered
    pre-enable telemetry look like proof of enablement). Anything else observed while confirming is
    tagged pre-enable: recorded in the raw report, never actioned as active-phase state. Caught a
    real bug in this revision's own regression test along the way: the original enable send's own
    single-packet reply can itself already be the real TargetUpdate; an early draft discarded it and
    waited for a second packet that would never come, timing out instead of confirming.
  - In --firmware-authoritative mode, Frozen firmware becomes the sole authority on pump sequencing,
    TEC ramping, PID control, solenoid control, fan control, current safety, thermal regulation, and
    target maintenance. The legacy loop's host-side heuristics (pump-startup-not-confirmed, the
    5s/20s/15s communication and temperature watchdogs, the generic fault-keyword scan, stopping
    early on target attainment) are all disabled in this mode -- replaced by a small, closed set of
    legitimate automatic stops: duration expiry, operator abort, a signal, an explicit TEC safety
    lock, an explicit recognized firmware safety-fault message, the enabled target being explicitly
    lost, a fatal UART error, an internal error, and one remaining, much longer (30s) communication-
    silence check.
  - A second, previously undocumented pump-message format was captured from the same incident:
    "[pump-left] slow=>6.500000" / "[pump-left] default=>9.000000" -- a dash-and-arrow
    pump-*command* format, distinct from the existing bracket-and-@ status format. Recognized as
    positive pump evidence; its "default" value re-confirms the word-exact fault-keyword fix from
    revision 15 still holds ("fault" is a literal substring of "default").
  - New independent shutdown guard (guard.rs, hidden internal-cool-test-guard subcommand): armed
    only once the target is confirmed enabled and only for a real run, it re-execs the packaged
    binary as a genuinely separate OS process -- not a thread, since an in-process construct shares
    fate with whatever it's meant to protect against. Races an arm timer (requested duration + 30s
    grace) against a disarm byte on its own stdin pipe; if the main process's own verified shutdown
    never disarms it, it opens the real Frozen UART/I2C itself and runs the same disable sequence
    every other shutdown path in this tool uses.
  - Unchanged: default duration (120s), hard maximum (900s), 2.0C delta cap, all required
    confirmations, baseline collection/validation.

What changed in revision 15
----------------------------
Even after revision 14 fixed the TEC-lock substring bug, a live cooling test still shut down
immediately on "FW: tec[left] safe, unlocking". Root cause: STALE_TELEMETRY_LIMIT (2s, refreshed
only by unsolicited TemperatureUpdate) was shorter than this firmware's own unsolicited-push
cadence (~10s, per revision 13's finding) -- the TEC message and the shutdown were coincidentally
close in the log; the watchdog fired on schedule, not because of the TEC message.

  - Replaced the single clock with four independent ones and three real-hardware-sized limits:
    ANY_VALID_RX_LIMIT (5s, any decoded packet), TEMPERATURE_FRESHNESS_LIMIT (20s, once a first
    active-phase temperature sample has been seen), ACTIVE_STARTUP_GRACE (15s, before the first
    one has). New StopReason variants CommunicationWatchdogExpired/TemperatureWatchdogExpired/
    TemperatureStartupGraceExpired.
  - A synchronous GetTemperatures response (both byte shapes) is no longer "raw evidence only"
    during the active phase -- new shared helper record_active_temperature_sample processes it
    identically to the unsolicited push, including refreshing the temperature watchdog.
  - Fixed the active loop trying the safety-state parser on every TEC-tagged message
    unconditionally, including plain current readings, which produced a spurious "unrecognized
    TEC safety-state message" warning on every reading. TEC-tagged messages are now routed by
    type: current is tried first, safety-state only if that doesn't match.
  - Removed TecSafetyState::is_fault()/is_safe_transition() entirely: even with a correct parser,
    the caller's own control flow was the actual bug in an earlier draft of this fix. Every call
    site (including tests) now writes an exhaustive match over all five variants.
  - Found by this fix's own regression test: "fault" is a substring of "default", and the real,
    benign message "FW: pump[left] default @ ...V ...A" was misclassified as FirmwareFaultMessage.
    Fixed the same way as "locked"/"unlocked": word-exact match via WORD_EXACT_FAULT_KEYWORDS.
  - Every controlled shutdown now logs "beginning controlled shutdown: stop_reason=<code>" from
    inside run_cool_test_shutdown itself (the sole function every exit path calls), and reports a
    new stop_reason_code field in text/JSON/CSV.
  - frozen-cool-test --dry-run's shared mock device now also pushes the exact captured TEC
    current/"safe, unlocking" sequence once a side is enabled, so this is exercised by the actual
    packaged ARM64 binary under qemu-aarch64-static, not only cargo test.
  - Unchanged: default duration (120s), hard maximum (900s), 2.0C delta cap.

What changed in revision 11
----------------------------
A live run of revision 10's --release-frozen-only pulsed register 0x02 correctly (readbacks all
verified, 0xFD -> 0xFF -> 0xFD) and Frozen still never responded. Register 0x06 (direction/config)
was never touched by that revision. On the PCAL6416A, register 0x06 selects per-bit whether a pin
is an input/high-impedance (1) or an output (0); the power-on-reset default is every bit an input,
which ignores its output-latch value (register 0x02) entirely -- so revision 10's pulse changed
what the chip would drive if bit 1 were an output, not the physical pin. The original,
confirmed-working upstream reset sequence writes register 0x06 to 0xFC (bits 0 and 1 as outputs) as
one of its first two writes; this mode's narrow, bit-1-only analog of that write was missing.

    0x02's output latch to the asserted level before bit 1 becomes an output, avoiding an
    unintended glitch; (2) configures only bit 1 of register 0x06 as an output, preserving bit 0
    and every other bit; (3) holds the now-actually-driven level for 100ms, then releases it.
    Every write's target is verified mathematically before being issued (generalized from a
    register-0x02-only helper to a shared one accepting either register) and every readback is
    verified after. Register 0x06 is deliberately never restored -- the reset line must stay
    actively driven -- and register 0x07 is still never written.
  - `report::ReleaseFrozenOnlyResults` gained `original_register_0x06`/`config_register_0x06`/
    `config_readback_register_0x06`/`config_readback_matches`/

operate) is in PROTOCOL_AUDIT.md. Key findings that shaped the implementation:

  - `Prime` takes no arguments and has no per-side field -- it always affects both sides in one
    frame (`7E 01 52 B6 2B`, asserted byte-for-byte by upstream's own test_prime fixture). This is

    "priming complete" packet, so this mode's early-stop-on-completion logic is driven entirely by
    that message text.
  - No Prime-cancellation command exists anywhere in the reused protocol (confirmed by a full scan
    of FrozenCommand's variants). Subsystem reset (I2C 0x20) is therefore the only forced-stop
    mechanism, exactly as for every other mode -- frozen-prime-test runs the same shared safe-stop
    routine on every exit path, including after "done" was already observed.

    "// TODO verify it actually started priming" comment acknowledging no reliable completion
    tracking exists upstream either. frozen-prime-test's 5-60s bounds (default 30s) are therefore a
    deliberately conservative compile-time choice, stated as such rather than presented as
    spec-derived.

    documented as a forward-compatible keyword scan, not a confirmed protocol feature.

    delivered build): an over-throttled telemetry-polling cadence that was incompatible with the
    2-second staleness threshold, and a pre-existing bug (also affecting frozen-cool-test, fixed
    here too) where several JSON report fields were being set on the in-memory Report *after* it
    had already been written to disk, so the file never reflected them. Both are covered by new
    automated tests and re-verified against the real cross-compiled binary via qemu-aarch64-static.

What changed in revision 4
---------------------------
Corrected `frozen-cool-test`'s active-test preflight and safety monitoring based on evidence from
a real `frozen-passive` run and closer reading of the exact upstream source. Full account in
PROTOCOL_AUDIT.md and TEST_RESULTS.md; summary:

  - `TemperatureUpdate.error` is a control-loop error term in degrees C, not a fault/status code
    (source doc comment: "error in deg celcius"; real captured telemetry consistently reports 9
    with no other sign of a fault). Renamed to `control_error_c` in JSON/CSV output and confirmed
    to never gate any pass/fail/abort decision -- `cool_test::evaluate_tick` doesn't even take
    this field as a parameter.
  - Baseline collection and active-phase safety monitoring now rely exclusively on the unsolicited
    `TemperatureUpdate` push (opcode 0x41), not the solicited `GetTemperature` reply (opcode
    0xC1): real hardware has been observed sending a 14-byte 0xC1 frame, while the reused,
    unmodified parser requires exactly 27 bytes and so never decodes it. The solicited reply is
    still requested each tick (via a new `FrozenLink::send_only` fire-and-forget primitive) and
    preserved/logged as raw evidence when it does decode, but nothing safety-relevant depends on
    it anymore.
  - `[capwater]`/`[flowrate]` sensor-unavailable firmware messages are recorded as warnings, not
    treated as fatal (observed persisting with the cover connected and the reservoir filled; flow
    itself is not exercised until a pump actually runs).
  - New evidence-gated active-phase abort conditions: the selected pump still reporting off/0V
    more than 3 seconds after being enabled; a firmware message reporting the selected TEC locked;
    Frozen disabling the selected side on its own; a firmware fault-keyword message
    (overtemperature/overcurrent/shutdown/fault/failed/locked) after a 2-second startup grace
    period, with a documented carve-out for the evidenced, benign "flash locked" message; and the
    operator typing a report of a leak/smell/noise (or the literal word ABORT) during the active
    phase, read from a background stdin watcher started only after every confirmation-phrase read
    is complete.
  - `frozen-cool-test`'s default duration changed from 15 to 10 seconds for a first test; the hard
    30-second maximum, the 2.0C max delta, and the 15-35C baseline range are all unchanged.
  - Pump operation can now be reported PASS (not just UNVERIFIED) from decoded firmware voltage
    evidence, and FAIL if the most recent such message reports 0V/off -- still never PASS merely
    because the enable command was accepted.

What changed in revision 3
---------------------------
Complete redesign from a single-pass, read-mostly Frozen+Sensor probe into a staged,
Frozen-only diagnostic with three explicit subcommands:

  opensleep-diagnostic frozen-passive
  opensleep-diagnostic frozen-cool-test
  opensleep-diagnostic emergency-stop

The Sensor subsystem and the LED controller's write path are no longer referenced anywhere in
this binary's source (verified at test time by main.rs's guardrail_tests, which scan this
binary's own source files for forbidden references). `frozen-passive` never enables an actuator
command and is safe with the cover disconnected and no water. `frozen-cool-test` intentionally
activates exactly one cooling channel, gated behind four required --confirm-* flags and two
exact typed confirmation phrases, hard-coded limits (max 2.0C delta, max 30s duration, 15-35C
baseline range) that no CLI flag can override, and a shared safe-stop routine (three repeated
disable-both-sides sends, UART flush, I2C reset assert) that runs on every exit path including
Ctrl+C/SIGTERM/SIGHUP, timeout, communication/telemetry errors, and (via a catch_unwind boundary
around the per-tick evaluation logic) an internal panic. `emergency-stop` is an independent,
config/MQTT/Sensor/LED-free fast path that best-effort-disables both sides and unconditionally
asserts the I2C reset, returning non-zero if that reset could not be confirmed.

`Prime` and `Random` are structurally unreachable: the closed FrozenAction enum
(src/bin/opensleep-diagnostic/safety.rs) has no variant for either, so this binary's own command
type cannot represent them, independent of any runtime whitelist. See SAFETY.md and
PROTOCOL_AUDIT.md for the full command/evidence audit.

A --dry-run flag on every subcommand performs no I2C or UART writes and instead runs the same
code paths against a mocked Frozen device and a mocked I2C bus, so the full flow (including the
interactive confirmations) is testable on an ordinary development machine.
