Patch revision: 5 (adds frozen-prime-test: Prime is now reachable in exactly one mode)
Supersedes revision 4 (corrected active-test preflight/monitoring), revision 3 (staged,

What changed in revision 5
---------------------------
Added a fourth subcommand, `frozen-prime-test`, which intentionally sends `Prime` (opcode 0x52)
exactly once to fill an empty or partially-filled hydraulic loop. Full source audit (does Prime
take arguments, apply to one/both sides, have an acknowledgment/start/completion signal, have a
cancellation command, or have an assumed duration; what pumps/valves/solenoids are expected to
operate) is in PROTOCOL_AUDIT.md. Key findings that shaped the implementation:

  - `Prime` takes no arguments and has no per-side field -- it always affects both sides in one
    frame (`7E 01 52 B6 2B`, asserted byte-for-byte by upstream's own test_prime fixture). This is
    why frozen-prime-test has no --side flag, unlike frozen-cool-test.
  - Direct start evidence: the binary `PrimingStarted` packet (0xD2) and/or a decoded
    "FW: [priming] start" message. The *only* completion evidence that exists anywhere in the
    protocol is "FW: [priming] done" / "...done because empty" -- there is no binary
    "priming complete" packet, so this mode's early-stop-on-completion logic is driven entirely by
    that message text.
  - No Prime-cancellation command exists anywhere in the reused protocol (confirmed by a full scan
    of FrozenCommand's variants). Subsystem reset (I2C 0x20) is therefore the only forced-stop
    mechanism, exactly as for every other mode -- frozen-prime-test runs the same shared safe-stop
    routine on every exit path, including after "done" was already observed.
  - Normal OpenSleep's own scheduler does not assume any priming duration: its `prime` config
    field is a time-of-day, not a duration, and its own source contains a
    "// TODO verify it actually started priming" comment acknowledging no reliable completion
    tracking exists upstream either. frozen-prime-test's 5-60s bounds (default 30s) are therefore a
    deliberately conservative compile-time choice, stated as such rather than presented as
    spec-derived.
  - No "solenoid" or "valve" message exists anywhere in the pinned source; that detection is
    documented as a forward-compatible keyword scan, not a confirmed protocol feature.
  - `Prime` is gated by two independent mechanisms: the existing per-mode whitelist (extended with
    a new `Mode::PrimeTest`), and a new at-most-once check inside `AuditedTransport::check` itself
    -- a second `Prime` attempt in the same run is refused at the transport layer, not merely
    avoided by this binary's own control flow. A new source-level guardrail test
    (`frozen_action_prime_is_referenced_only_in_safety_and_prime_test`) proves
    `FrozenAction::Prime`/`FrozenAction::prime()` is never referenced outside `safety.rs`/
    `prime_test.rs`.
  - `frozen-prime-test`'s result reporting never marks the run PASS merely because the command was
    sent, acknowledged, a pump showed voltage, or "done" was printed -- it requires either a direct
    firmware reservoir-transition message or the operator confirming both water movement and a
    dropped reservoir level; otherwise the result is INCONCLUSIVE.
  - Two bugs were found and fixed during this revision's own smoke-testing (not present in the
    delivered build): an over-throttled telemetry-polling cadence that was incompatible with the
    2-second staleness threshold, and a pre-existing bug (also affecting frozen-cool-test, fixed
    here too) where several JSON report fields were being set on the in-memory Report *after* it
    had already been written to disk, so the file never reflected them. Both are covered by new
    automated tests and re-verified against the real cross-compiled binary via qemu-aarch64-static.

What changed in revision 4
---------------------------
Corrected `frozen-cool-test`'s active-test preflight and safety monitoring based on evidence from
a real `frozen-passive` run and closer reading of the exact upstream source. Full account in
PROTOCOL_AUDIT.md and TEST_RESULTS.md; summary:

  - `TemperatureUpdate.error` is a control-loop error term in degrees C, not a fault/status code
    (source doc comment: "error in deg celcius"; real captured telemetry consistently reports 9
    with no other sign of a fault). Renamed to `control_error_c` in JSON/CSV output and confirmed
    to never gate any pass/fail/abort decision -- `cool_test::evaluate_tick` doesn't even take
    this field as a parameter.
  - Baseline collection and active-phase safety monitoring now rely exclusively on the unsolicited
    `TemperatureUpdate` push (opcode 0x41), not the solicited `GetTemperature` reply (opcode
    0xC1): real hardware has been observed sending a 14-byte 0xC1 frame, while the reused,
    unmodified parser requires exactly 27 bytes and so never decodes it. The solicited reply is
    still requested each tick (via a new `FrozenLink::send_only` fire-and-forget primitive) and
    preserved/logged as raw evidence when it does decode, but nothing safety-relevant depends on
    it anymore.
  - `[capwater]`/`[flowrate]` sensor-unavailable firmware messages are recorded as warnings, not
    treated as fatal (observed persisting with the cover connected and the reservoir filled; flow
    itself is not exercised until a pump actually runs).
  - New evidence-gated active-phase abort conditions: the selected pump still reporting off/0V
    more than 3 seconds after being enabled; a firmware message reporting the selected TEC locked;
    Frozen disabling the selected side on its own; a firmware fault-keyword message
    (overtemperature/overcurrent/shutdown/fault/failed/locked) after a 2-second startup grace
    period, with a documented carve-out for the evidenced, benign "flash locked" message; and the
    operator typing a report of a leak/smell/noise (or the literal word ABORT) during the active
    phase, read from a background stdin watcher started only after every confirmation-phrase read
    is complete.
  - `frozen-cool-test`'s default duration changed from 15 to 10 seconds for a first test; the hard
    30-second maximum, the 2.0C max delta, and the 15-35C baseline range are all unchanged.
  - Pump operation can now be reported PASS (not just UNVERIFIED) from decoded firmware voltage
    evidence, and FAIL if the most recent such message reports 0V/off -- still never PASS merely
    because the enable command was accepted.

What changed in revision 3
---------------------------
Complete redesign from a single-pass, read-mostly Frozen+Sensor probe into a staged,
Frozen-only diagnostic with three explicit subcommands:

  opensleep-diagnostic frozen-passive
  opensleep-diagnostic frozen-cool-test
  opensleep-diagnostic emergency-stop

The Sensor subsystem and the LED controller's write path are no longer referenced anywhere in
this binary's source (verified at test time by main.rs's guardrail_tests, which scan this
binary's own source files for forbidden references). `frozen-passive` never enables an actuator
command and is safe with the cover disconnected and no water. `frozen-cool-test` intentionally
activates exactly one cooling channel, gated behind four required --confirm-* flags and two
exact typed confirmation phrases, hard-coded limits (max 2.0C delta, max 30s duration, 15-35C
baseline range) that no CLI flag can override, and a shared safe-stop routine (three repeated
disable-both-sides sends, UART flush, I2C reset assert) that runs on every exit path including
Ctrl+C/SIGTERM/SIGHUP, timeout, communication/telemetry errors, and (via a catch_unwind boundary
around the per-tick evaluation logic) an internal panic. `emergency-stop` is an independent,
config/MQTT/Sensor/LED-free fast path that best-effort-disables both sides and unconditionally
asserts the I2C reset, returning non-zero if that reset could not be confirmed.

`Prime` and `Random` are structurally unreachable: the closed FrozenAction enum
(src/bin/opensleep-diagnostic/safety.rs) has no variant for either, so this binary's own command
type cannot represent them, independent of any runtime whitelist. See SAFETY.md and
PROTOCOL_AUDIT.md for the full command/evidence audit.

A --dry-run flag on every subcommand performs no I2C or UART writes and instead runs the same
code paths against a mocked Frozen device and a mocked I2C bus, so the full flow (including the
interactive confirmations) is testable on an ordinary development machine.
